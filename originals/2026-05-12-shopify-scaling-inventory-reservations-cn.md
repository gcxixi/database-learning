# 我们在库存预占中用 MySQL 替换了 Redis —— 而且它成功抗住了超大规模流量

> **原文标题**: We replaced Redis with MySQL for inventory reservations—and it scaled  
> **作者**: Emilie Noel ([Engineering at Shopify](https://shopify.engineering))  
> **发布日期**: 2026年5月12日  
> **原文链接**: [https://shopify.engineering/scaling-inventory-reservations](https://shopify.engineering/scaling-inventory-reservations)  
> **核心导读**: 探讨 Shopify 如何利用 MySQL 8 的 `SKIP LOCKED`、复合主键（Composite Primary Keys）以及连接可见性（Connection Visibility）达成极限规模下的扩展目标。

---

在结账过程中，当买家点击“完成购买”（Complete purchase）时，我们必须百分之百保证他们正在购买的商品仍然有库存。

- 如果我们在一个方向上出现差错，就会导致**两位买家同时买下同一件库存商品（超卖）**：商家不得不被迫取消订单、发送道歉邮件，并独自承担客户支持成本。
- 如果我们在另一个方向上出现差错，我们就会**向买家误报某件明明有库存的商品已售罄（少卖）**：商家将白白错失原本唾手可得的销售收入。

在 Shopify 如此庞大的业务规模下，任何一种错误都会被迅速成倍放大。在 **2025 年黑色星期五（Black Friday 2025）**期间，我们平台上的商家在峰值期创下了**每分钟 510 万美元销售额**的惊人纪录。而这其中的每一笔交易，都在直接与库存系统发生交互。

我们的**防超卖系统（Oversell Protection System）**通过在支付处理期间对库存进行“预占”（Reservation）来应对这一挑战——这是一种短暂的锁定（Short Hold），能够阻止两个并发结账请求同时声明抢占同一件商品。

多年以来，这套预占系统一直运行在 **Redis** 之上。然而，当我们着手推进统一数据库战略（Unified Database Strategy）时，不得不面对并回答一个非常艰难的技术问题：**MySQL 能够承受住同等量级的流量规模吗？**

我们早期的几次尝试均以失败告终。当时的设计采用“单行记录配合数量列（A single row with a quantity column）”，在激烈的行锁争用（Contention）面前不堪重负。然而，MySQL 8 引入的 `SKIP LOCKED` 特性为我们打开了一种截然不同的设计思路：**由“每个商品一行记录”转变为“每个库存单元一行记录”（One row per inventory unit instead of one row per item）**。

受到 37signals 利用数据库进行负载分发思想的启发，我们在 MySQL 上重构了整个预占系统，并在 2025 年的黑五流量高峰期间稳稳达成了超高吞吐量的性能指标。

但在这个过程中，我们学到的最深刻教训并非单纯来自数据库设计本身，而是发现**真正的系统瓶颈，根本不在我们平时重点观察和度量的那些指标上**。

本文将详细拆解这套技术方案，以及我们在沿途探寻中所获得的核心发现。

---

## 挑战所在 (The Challenge)

### 什么是防超卖？ (What is oversell protection?)

防超卖机制主要包含两项核心操作：

1. **预占 (Reserve)**：当支付流程启动时，我们将对应的商品标记为预占状态（保留一个短暂的持有期，例如数分钟）。
2. **核销认领 (Claim)**：当支付确认成功后，我们从库存持久账本（Inventory Ledger，系统的真理之源 Source of Truth）中永久扣减对应数量。

结账链路的顺利完成，极度依赖于这一过程的**极速响应**与**绝对正确**。慢速的预占操作会触发系统限流，给买家带来糟糕的结账体验；而出现逻辑差错则意味着发生超卖（引发买家愤怒）或少卖（造成商家收入损失）。

### 规模与正确性要求 (Scale and correctness requirements)

在这里，规模绝不是一个抽象的名词：Shopify 支撑着美国超过 14% 的电商流量；在 2025 年黑五高峰期，我们见证了峰值每分钟销售额同比前一年再度增长 11%。每一笔涉及库存的结账都会触发预占操作，因此整个系统必须在高并发突发流量下既不丢弃任何请求，也不能打破数据一致性。

我们的系统需要做到：
- 在流量峰值期间支撑平台严苛的高性能吞吐目标；
- 适配**多履约中心/多地点库存（Multi-location Inventory）**，仅允许从具备实际发货能力的地点进行预占；
- 在预占状态与底层库存持久账本之间保持严格的 **ACID 事务保证**；
- 始终将**正确性**置于首位：杜绝超卖，绝不遗失预占记录。

### 历史 Redis 模型及其局限性 (The Redis model and its limits)

我们先前的系统将预占数据存放在 Redis 中。每个商品对应一个代表数量的 Key，预占操作执行 `DECR`，释放操作执行 `INCR`。

Redis 处理纯内存并发确实非常游刃有余，但问题在于：**预占数据与底层库存持久账本分别驻留在两个完全独立的系统中**。

当进行“核销认领”（支付成功后永久扣减库存账本）步骤时，系统必须既更新 MySQL，又要清理 Redis 中的预占状态。然而，**这两项跨系统的操作根本无法被封装进一个原子的步骤中**。根据执行顺序的不同，可能会引发两类经典异常：
- **超卖**：商品已被买家买走，但从未成功在底层 MySQL 账本中扣减；
- **少卖**：商品已在 MySQL 账本中扣减，但 Redis 里的预占记录未能及时清理，导致库存长久悬挂。

除此之外，原有的 Redis 模型无法感知多履约地点的库存拓扑，同时还带来了需要独立维护一套专用 Redis 集群的高昂运维成本。

如果能将预占操作直接迁移至存放账本的同一套 MySQL 数据库中，我们就能将所有操作包裹在原生的 ACID 事务之中，从而**从根本上彻底消灭这些跨系统失效模式**。

## 解决方案：SKIP LOCKED

### 核心思想：每单元一行记录，有界容量设计 (Core idea: one row per unit, bounded by design)

我们推翻了传统的“一个商品对应一行记录并带有一个 `quantity` 字段”的做法，转而采用**“每个可售库存单元占用一行记录”**的模式。

举例来说：如果某件商品有 10 件库存，表中就会存在 10 行独立的记录。当买家需要预占 3 件商品时，系统只需在单个事务中通过查询选取并转移其中的 3 行数据。通过将预占与库存账本收敛在同一个数据库内，我们在预占与核销全生命周期中均获得了严格的 ACID 保障，彻底修复了此前在 Redis 架构下可能出现的各类逻辑缺陷（例如支付成功却未核销库存，或反之）。

一个简化后的预占 SQL 流程如下所示：

```sql
-- 开启事务，使用 READ COMMITTED 隔离级别
BEGIN;

-- 选取 N 个库存单元，自动跳过已被其他并发事务锁定的行
SELECT id
FROM available_units
WHERE shop_id = ?
  AND inventory_item_id = ?
  AND inventory_group_id = ?
ORDER BY shop_id ASC, inventory_item_id ASC, inventory_group_id ASC, id ASC
LIMIT 3
FOR UPDATE SKIP LOCKED;

-- 将选中的单元记录转移写入 reserved_units 预占表
INSERT INTO reserved_units (unit_id, cart_token, expires_at, ...)
VALUES (...);

-- 从可用库存单元池中移除这些记录
DELETE FROM available_units
WHERE (shop_id, inventory_item_id, inventory_group_id, id) IN (?, ?, ?, ?);

COMMIT;
```

**`SKIP LOCKED` 正是让这套设计能够具备横向扩展能力的关键钥匙**：如果某几个数据行已经被其他并发事务加锁持有，MySQL 会直接跳过它们，转而返回其他未被锁定的空闲行。事务之间无需在同一行数据上苦苦排队等待，行级锁争用随之大幅骤降。

然而，如果为所有库存统统无脑采用“一单元一行”的物理映射，在超大规模下必然会崩溃：一件分布在 10 个仓库、拥有 50,000 件库存的商品，将直接膨胀出 500,000 行记录，导致预占查询在扫描这些记录时性能急剧劣化。

为了解决这一问题，我们构建了一个**有界可用行缓冲池（Bounded Pool of Available Rows），将每个“商品/地点”组合在表中的记录上限严格限制在 1,000 行**。预占操作只从这个缓冲池中消费行；随后的补货流程（Replenishment Process）则会根据需要从底层真实的库存账本中向缓冲池注水补充记录。

**为什么设定为 1,000？**  
这个上限值既要足够大，以充分吸收高并发突发瞬时流量而不至于快速打空；同时又要足够小，以保证数据表足够紧凑、`SKIP LOCKED` 的扫描足够迅速。我们根据在秒杀闪购活动中观察到的单商品/地点峰值预占速率确定了这一数值：**1,000 行的缓冲区提供了充裕的安全余量，使得后台补货流程在持续高负载下能够完全跟得上消费节奏，同时避免了数据表过度膨胀拖垮查询性能**。

**如果缓冲池被彻底打空了怎么办？**  
在极端的秒杀闪购场景下，某个爆款商品的缓冲池可能被瞬时耗尽。一旦发生这种情况，预占链路将会在调用链中**就地内联触发补货（Inline Replenishment）**。我们通过一把互斥锁确保同一时刻只有一个事务能够执行补货操作；其他正在并发预占该商品的事务会耐心等待补货完成，而不是蜂拥而上同时争抢执行插入，从而巧妙地避免了**惊群效应（Thundering Herd）**。一旦补货完成，所有排队的事务便能立即从充满的缓冲池中顺利获取数据行。买家绝不会被误判为“无库存”（除非真实账本确实已耗尽）。虽然这会给触发补货的个别预占请求增加一定的时延，但它换取了绝对的业务正确性：**只要还有实际库存，买家就永远不会被无辜拒之门外**。

## 关键技术决策 (Key Technical Decisions)

### 1. 复合主键：减少单行锁定数量 (Composite primary key: fewer locks per row)

在我们最初的原型设计中，数据表使用了自增 ID 作为主键。然而，当我们利用 `SHOW ENGINE INNODB STATUS` 等手段深入观察加锁行为时，震惊地发现：**每次预占操作竟然产生了 2 个行锁，而不是预期的 1 个**。

在自增主键的结构下，InnoDB 不仅对我们在 `WHERE` 条件中使用的二级索引（Secondary Index）加了行锁，而且在通过主键回表时对聚簇索引（Clustered Index，即主键）也加了锁。

针对这一问题，我们将主键重构为**复合主键（Composite Primary Key）**：
```sql
PRIMARY KEY (shop_id, inventory_item_id, inventory_group_id, id)
```
由于过滤条件所依赖的所有列都直接成为了聚簇索引的一部分，加锁直接在主键树上完成，**将每次预占的行锁数量精准砍半至每个单元仅 1 个行锁**。在每秒需要处理海量并发预占的极端场景下，这一优化对吞吐量的提升至关重要。

> **核心经验**：在极端高并发规模下，索引与主键的设计形态直接决定了行锁的数量与系统的并发吞吐上限。

### 2. READ COMMITTED：杜绝间隙锁与伪记录锁 (READ COMMITTED: avoiding gap / supremum locks)

当我们对一个空表或者需要补货的数据范围执行 `SELECT ... FOR UPDATE SKIP LOCKED` 时，遇到了严重的**间隙锁（Gap Locks）**，甚至包括作用在 `supremum` 虚拟伪记录上的锁。这些间隙锁阻断了并发补货事务向表中插入新行，极易引发死锁连锁反应。

为此，我们将这些关键事务的隔离级别从 **MySQL 默认的 `REPEATABLE READ`（可重复读）降级调整为 `READ COMMITTED`（读已提交）**。

在 `READ COMMITTED` 隔离级别下，InnoDB 在普通索引扫描时不会像 RR 那样施加间隙锁，因此并发的补货插入事务得以顺畅执行。Jahfer Husain 关于 InnoDB 锁机制的经典指南为我们厘清这一原理提供了巨大帮助。这也是我们在该代码库中首次打破常规使用非默认的隔离级别，为此我们在底层框架层增加了针对单个事务动态设置隔离级别的细粒度支持。

### 3. 严格一致的加锁顺序：彻底根除死锁 (Consistent lock ordering: avoiding deadlocks)

当“预占（Reserve）”与“核销（Claim）”两个动作以不同顺序访问两张数据表时，我们不可避免地遭遇了死锁。
- 原先的预占链路是：先向 `reserved_quantities` 执行 `INSERT`，再从 `reservation_units` 执行 `DELETE`；
- 而核销链路则是：直接从 `reserved_quantities` 执行 `DELETE`。

当不同事务以相反或交错的顺序获取这两张表的锁资源时，死锁闭环随之产生。

解决方案是将所有涉及表的加锁时序进行**严格标准化（Standardize the Order）**：
- 预占链路**永远先**从可用单元表（`reservation_units`）执行 `DELETE`，**随后再**向预占表（`reserved_quantities`）执行 `INSERT`；
- 核销链路则**仅严格访问** `reserved_quantities`。

由于所有执行路径都遵循完全一致的加锁先后顺序，任何事务都不会在持有对方所需锁的同时去等待对方持有的锁——**资源循环等待条件（Circular Wait）被彻底打破，死锁因此荡然无存**。

### 4. 基于 UNION ALL 的购物车批量预占 (Batching with UNION ALL)

每一次与数据库的网络往返（Round Trip）都有不可忽略的通信与协议成本。对于包含多个不同 SKU 明细项的复杂购物车，我们通过 `UNION ALL` 将针对不同商品的预占查询整合在单条 SQL 中批量发起：

```sql
(SELECT id, inventory_item_id, inventory_group_id
 FROM available_units
 WHERE shop_id = 1 AND inventory_item_id = 100 AND inventory_group_id = 1
 ORDER BY shop_id, inventory_item_id, inventory_group_id, id
 LIMIT 2 FOR UPDATE SKIP LOCKED)
UNION ALL
(SELECT id, inventory_item_id, inventory_group_id
 FROM available_units
 WHERE shop_id = 1 AND inventory_item_id = 200 AND inventory_group_id = 1
 ORDER BY shop_id, inventory_item_id, inventory_group_id, id
 LIMIT 5 FOR UPDATE SKIP LOCKED)
```

这显著削减了端到端的网络往返次数，大幅降低了高负载下的请求延迟。

## 真正的瓶颈：是连接数，而不是 CPU (The Real Bottleneck: Connections, Not CPU)

在最初的生产压测中，我们遭遇了一个远低于预期目标的吞吐量天花板。

当时我们排查了一圈：预占延迟（例如 P90 指标）表现非常健康，数据库 CPU 利用率甚至远未饱和，且所有的 SQL 语句都已经过了极致调优。既然如此，瓶颈到底卡在哪里？

我们曾尝试将多个不同结账请求的预占操作合并到单条 `SKIP LOCKED` 查询中以节省连接，这在基准测试中虽然有效，但引入了巨大的系统复杂度；我们也尝试将部分纯读流量拆分卸载到从库（Read Replicas）。然而，整个系统的表现依然不符合常理。

### 抽丝剥茧：顺着病症追踪 (Following the symptoms)

在持续的加压测试中，我们观察到如下异常现象：
- MySQL 内部大量线程处于排队状态（Threads queuing）；
- 当这些排队的任务被集中放行处理时，CPU 会出现瞬时剧烈脉冲；
- ProxySQL 数据库代理层通往 MySQL 后端的主连接池出现连接耗尽（Connection Exhaustion）。

这促使我们下定决心为系统引入全新的观测维度：**精确度量究竟是哪一个业务进程持有数据库连接，以及分别持有了多久**。

仅仅知道“连接池耗尽了”没有任何指导意义，因为它无法告诉你究竟是谁把连接霸占不放。我们需要具备针对**具体调用者（Per-caller Attribution）**的归因能力。

1. **应用层打标**：我们在应用层为发往数据库的每一条 SQL 语句添加了业务注释标签，例如：  
   `/* conn_tag:checkout_completion */`
2. **代理层统计**：在 ProxySQL 代理层，我们增加了专门的解析跟踪模块，负责提取 SQL 中的 Tag，并精确记录该调用方在整个连接生命周期中所持有时长。

这一改造的产出立竿见影：**我们获得了按具体业务进程维度精准细分的大盘总连接持有时间指标（Total Connection Hold Time）**。

监控仪表盘清晰地揭示了到底是哪些调用者消耗了绝大部分连接时长——**这不是在找“哪些 SQL 执行缓慢”，而是在找“哪些业务流程在横跨长事务期间无谓占有着底层物理连接”**。如果你也遇到了连接数瓶颈且束手无策，这种“应用层打标 + 代理层聚合”的架构模式非常简单易行，且能立刻提供关键决策依据。

### 真正的破案发现 (What we found)

一旦连接持有的全貌被清晰展现，我们赫然发现：**预占操作根本不是连接资源的重度霸占者！**

结账链路中的其他无关环节在长事务期间持有数据库连接的时间，远远超出了合理范围。由于那些代码在以往的历史中从未率先踩中过系统极限，因此它们一直被团队所忽视。

然而，数据库连接资源是极其有限的：在超高并发吞吐场景下，我们迫切需要每秒周转海量的“超短平快事务”。当其他冷门代码无休止地拖延并占用连接时，预占业务的到来便成为了“压垮骆驼的最后一根稻草”——**这根本不是因为预占逻辑变慢了，而是因为连接池早已被其他流程蚕食殆尽**。

摸清根因后，我们针对整个结账关键路径展开了雷厉风行的瘦身治理：
- **直接消除了主库上 50% 的读操作以及 33% 的事务**；
- 重新审视并调优了 MySQL 的核心配置：许多年前由于保守考虑而设定的 `innodb_thread_concurrency`（InnoDB 线程并发度）此后从未被重新评估过。随着硬件与负载特征的剧烈变化，在确认系统具备充足算力余量后，我们果断调大了该并发度参数，彻底消除了这项我们此前在缺乏连接与 CPU 联合监控时从未察觉的隐形瓶颈。

这两项重大改进（链路清理与参数优化）彻底打破了原先压制吞吐的天花板，系统的扩展能力远超既定目标。在后续的高并发秒杀闪购实测中：
- **主库（Writer）CPU 利用率稳定保持在 50% 以下**；
- **从库（Reader）CPU 利用率更是低至 16% 以下**；
- 系统展现出了极其充裕的性能吞吐余量。

## 生产割接与平滑上线 (The Cutover)

在将系统从 Redis 迁移到 MySQL 的过程中，我们绝不是简单粗暴地“一键切开关”。

我们采用了被称为**“影子模式（Shadow Mode）”**的双轨并行运行策略：
- 每一笔预占请求同时并发写入 Redis 和 MySQL；
- 在整个演进阶段，**Redis 始终保持为真理之源（Source of Truth）**；
- 这使我们能够将两个系统在生产真实流量下的运行表现进行像素级的逐笔比对，从容验证 MySQL 在真实世界中产出的业务数据是否百分之百正确，并检验其性能指标是否达到生产标准。

由于两套系统同时在线承接流量，我们甚至完全不需要迁移任何正在在途运行中的历史预占数据：**旧的 Redis 预占自然超时或完成核销，而 MySQL 则在并行运转中平滑建立起自己的最新状态机**。

当我们对 MySQL 的正确性与性能表现感到百分之百笃定时，才正式将真理之源平滑切换至 MySQL。即使上线后发生任何意料之外的险情，我们也可以通过一键熔断开关（Kill Switch）瞬间回退至 Redis——因为双写通道一直在持续工作，Redis 始终保留着当前全量预占状态的最新切片。

整套切换采用了按 Pod 逐步放量的分阶段灰度策略：先从低流量 Pod 试水，随后逐步平滑推进至平台上交易量最大的超级头部商家。

## 核心反思与工程经验 (What We Learned)

我们从这次浩大的架构演进项目中收获良多，其中最重要的两条经验是：

### 1. 敢于重新审视历史决策 (Revisit old decisions)

五年前在技术上被判定为“不可能”（例如用 MySQL 扛起这套超高并发预占负载）的方案，在今天随着数据库新特性（如 `SKIP LOCKED`）的引入已经变得完全可行。

对数据库的配置调优同样如此：随着硬件架构与业务负载形态的不断演化，过去那些被奉为圭臬的“经验法则”参数设置非常值得定期拿出来重新审视。**当监控大盘中的指标逻辑出现矛盾时（例如 CPU 利用率极低但排队等待队列却极高），务必顺藤摸瓜一查到底**。

### 2. 从极简原型切入，贴地深入观察 (Start small and observe)

我们在项目初期通过一个极其简陋的最小化原型获益匪浅：仅仅由一段简短的 Ruby 脚本与本地 MySQL 构成，完全摒弃了像 Rails 这类庞大繁杂的开发框架。

通过在另一个终端窗口中直接使用原生工具观测数据库的实时底层行为（例如并发加锁动态），我们所汲取到的知识远比纯粹研究纸面理论要丰富和深刻得多。**在技术探索期，极简的原型工具与极致紧凑的反馈闭环，永远胜过庞大而黑盒的复杂系统**。

## 结语 (Conclusion)

今天的现代 MySQL 完全有能力从容处理那些过去我们曾武断地认为必须借助专用外部组件才能解决的高难度负载。**如果你正打算引入 Redis、Kafka 或自研复杂的分布式协调层来实现高并发互斥，不妨先停下来深入看看：你现有的关系型数据库或许早已具备了解决该问题的全部能力**。

此外，**系统的真实瓶颈往往不在你直觉预设的地方**。我们曾花费数周时间对 SQL 语句与锁行为进行极致压榨，但最终真正的吞吐杀手却是那些我们甚至从未正眼看过的业务代码对底层连接的无谓占用。当指标对不上时——CPU 闲置但排队冲天——请务必对整个调用链路进行全景透视打标。答案往往藏在底层的“水暖管道（Plumbing）”里，而不是引擎本身。

最关键的一点在于：**这套重构的核心目的并不是单纯为了让预占自身变得更快，而是为了让它成为一个“人畜无害的好邻居（Safe Neighbor）”**。

在真实的电商生产环境中，预占系统必须与购物车更新、支付确认处理以及核心订单创建共享同一套底层数据库实例。一个肆意打满连接池或长时间霸占锁资源的恶邻系统，会直接将周围所有兄弟业务拖入深渊。我们真正追求的黄金标准，是**在持续提供海量极限吞吐的同时，守护好整座数据库的健康基底**。

对于 Shopify 而言，这项工程的回报无比坚实：更具韧性的库存预占，意味着彻底杜绝超卖，并帮助全球商家成功促成更多原本不应错失的交易。
